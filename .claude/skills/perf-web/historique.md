## Web Vitals mobile — Phase 1, quick wins globaux (2026-07-28)
Même chantier que ci-dessus, causes identifiées sur `/register` (LCP 4551ms) et `/today` (INP 2017ms, le pire de toutes les pages mesurées) via 3 agents d'investigation en lecture seule, puis un agent de planification. Détail complet et données chiffrées dans le plan `/Users/Gildas/.claude/plans/harmonic-dancing-possum.md`.

- **Fonts → `next/font/google`** (`src/app/layout.tsx`, `globals.css`, `tailwind.config.ts`) : remplace l'`@import url('fonts.googleapis.com/...')` (chaîne bloquante HTML→CSS→@import→2 origines externes, cause probable du CLS élevé partout — FOUT sur les titres en graisse 900/950, fallback Helvetica Neue→DM Sans). Self-host + preload auto via `next/font`, plus de requête réseau bloquante. Variable CSS `--font-dm-sans` posée sur `<html className={dmSans.variable}>`, consommée par `globals.css`/`tailwind.config.ts`.
- **Preconnect** (`layout.tsx`) : `eu.i.posthog.com`, `www.theperfclub.com`, `js.stripe.com`.
- **Stripe en lazy-load** (`PaywallModal.tsx`) : `loadStripe(...)` s'exécutait auparavant au chargement du **module**, importé en haut d'`OnboardingFlow.tsx` — le SDK Stripe se chargeait donc dès `value_intro` (1er écran), bien avant le paywall, en concurrence avec l'image LCP. **Fix** : singleton lazy `getStripePromise()`, appelé seulement au step `paywall_form` (guard déjà existant sur le fetch `setup-intent`, ligne ~1269). Comportement Stripe inchangé, seul le timing change.
- **Image LCP `value_intro`** (`OnboardingFlow.tsx`, `<img>` du carrousel, 1er slide toujours la même image statique) : `fetchpriority="high"` + `loading="eager"` sur cette image précise (attribut DOM brut via spread `{...{ fetchpriority: "high" }}`, React 18 ne reconnaît pas la prop camelCase), plus un `<link rel="preload" as="image">` posé côté Server Component (`register/page.tsx`, uniquement pour les visiteurs sans `?role=` — ce cas saute `value_intro`).
- **`next/dynamic` sur les 5 modales de `/today`** (`WellnessModal`, `AddSessionModal`, `CompleteModal`, `PaywallModal`, `PrimingJourneyModal`) : jusque-là importées statiquement dans `TodayClient.tsx` alors que rendues seulement sous condition — tout leur JS était hydraté avec le bundle principal. Premier usage de `next/font`/`next/dynamic`/`React.cache()` dans tout le repo (aucun précédent avant ce chantier).

**Non fait, volontairement** : split structurel de `TodayClient.tsx` (747 lignes, 11 `useState` sans mémoïsation — cause la plus probable de l'INP 2017ms) et `OnboardingFlow.tsx` (2626 lignes). Jugé trop risqué sans suite de tests automatisée sur des fichiers aussi centraux (funnel de conversion, dashboard principal) — à ne déclencher que si les fixes ci-dessus s'avèrent insuffisants une fois mesurés sur PostHog (1-2 semaines de données p90 pour lisser le bruit). Mémoïsation ciblée (`useMemo` sur `buildDotMap`) et fix CLS du bandeau d'activation (`showActivation`, résolu par `localStorage` dans un `useEffect` post-montage) identifiés mais pas implémentés — voir le plan pour le détail.

## Poids des bundles + code mort (2026-10-27)
Deux commits : `65d2a0d` (nettoyage) et `f70666b` (bundles). Mesure = JS au premier chargement, gzip, build de prod : layout racine 294→255 Ko (toutes les pages), `/register` 485→459, `/today` 537→506, `/coach/athletes` 410→381, `/programmes` 574→537.

- **Un import statique annule un `next/dynamic`** : si un composant chargé d'office importe la modale (ou n'importe quel export de son module, même une constante), elle repart dans le bundle initial. Cas trouvés : `ProfileDrawer` importé d'office dans `TodayClient` (il embarquait `PaywallModal`/Stripe), `PAYWALL_AVATARS` importé depuis `PaywallModal` par `OnboardingFlow` (Stripe dès le 1er écran d'inscription → déplacé dans `paywall/paywallAvatars.ts`), `athleteStatus`/`AthleteRing` importés depuis la page `AthletesClient` (toute la page coach dans l'inscription → `athleteStatus` vit dans `components/coach/AthleteRing.tsx`). **Règle : ne jamais importer depuis un fichier de page (`app/**/XClient.tsx`) ni depuis une modale lourde ; sortir le morceau partagé dans un petit module.**
- **Lecteur de démos** : `DemoSheetLauncher` (layout racine) écoute `DEMO_SHEET_EVENT` (`lib/demoSheetEvent.ts`, module sans dépendance) et ne charge `DemoSheetHost` (base Catalyst, parseur, banque d'exercices) qu'au premier tap, en lui passant ce tap via `initial`.
- **Auth** : `getAuthUser()` (`lib/supabase/server.ts`, `React.cache`) partagé par le layout `(app)` et ses pages, un `auth.getUser()` par rendu au lieu de deux.
- **Polices OG** : `outputFileTracingIncludes` limité à `/share/**` (vérifié dans les `.nft.json` du build : les fonctions `/share` contiennent toujours `DMSans-*.woff`).
- **Code mort retiré** (repéré avec knip) : 21 exports sans appelant, `driver.js`/`react-hot-toast`/`zustand`, 4 scripts ponctuels déjà exécutés (bibliothèque, patch de difficulté).
- **Limite hors ligne** : un chunk différé jamais ouvert en ligne n'est pas dans le cache du service worker (cache-first à la demande, pas de précache). Concerne désormais aussi `ProfileDrawer`/`DuplicateModal` sur `/today` (déjà le cas avant pour check-in, ajout de séance, RPE).
- **Non fait** : posthog-js ≈ 96 Ko gzip sur toutes les pages (28 fichiers l'importent directement) ; données de démos encore chargées par l'inscription via les aperçus de séance (`EliteSteps` → `SessionTemplateCard`), usage légitime.
- **Région des fonctions = `dub1` (Dublin)**, `vercel.json` `regions` (commit `bf885f5`, accepté sur le plan Hobby) : elles tournaient à `iad1` (Washington) alors que Supabase est en `eu-west-1` (Irlande) et les utilisateurs en France. Route à une requête : ~0,57 s → ~0,29 s en médiane. Vérifier la région servie via l'en-tête `x-vercel-id` (`cdg1::dub1::…`). Web Vitals PostHog avant ce changement (mobile, 30 j) : `/today` app iOS LCP médian 4,75 s / p75 6,1 s, web p75 2 s, `/register` p75 2,5 s, `/p/` direct 0,8 s (dans l'iframe WP 16-21 s, artefact probable du rendu différé des iframes hors écran). À remesurer d'ici 1-2 semaines.
- **Mesurer** : builder dans une copie hors du repo (un `next build` écrase le `.next` du serveur de dev), puis sommer la taille gzip des chunks de `app-build-manifest.json` pour `/layout` + la page.
- **Statut (27/10) : chantier clos**, sauf une remesure des Web Vitals PostHog vers le 10/11 (`/today` app iOS, mobile, p50/p75 LCP). Nettement sous 5 s → clos. Toujours ~5 s → la cause est ailleurs (piste : synchro Apple Santé à l'ouverture ou contenu qui s'affiche après coup sur l'app iOS), enquête séparée. **Volontairement non faits** : chargement différé de posthog-js et allègement de l'inscription (gain faible face au risque de perdre des events de funnel) ; découpage de `TodayClient`/`OnboardingFlow` (trop risqué sans tests automatisés).

## Audit performance & optimisations rapidité de chargement (2026-09-18)

Point de départ : demande d'audit performance général ("rendre l'app plus rapide, pas besoin de refresh pour voir des mises à jour") — analyse statique du code (bundle, rendu, fetch de données, temps réel) d'abord, sans exécution, puis mesure réelle via PostHog (événements `$web_vitals`, HogQL, clé API personnelle de Gildas fournie en session) avant toute correction, plutôt que de deviner les priorités.

### Diagnostic — données réelles PostHog (90j, p75/p90)
- `/p/[id]` (programmes publics, iframe WP, fort trafic anonyme) : LCP p75 **8 000-25 000ms**, p90 jusqu'à 48 000ms — régression nette depuis début août (2,5s le 02/08 → 23,5s le 23/08 → ~10-11s stabilisé depuis), alors que le fix TTFB de juillet 2026 (middleware court-circuité, `revalidate=60`) était toujours en place dans le code.
- `/week` Desktop : CLS p75 **0.54** (seuil "mauvais" Google > 0.25) ; `/coach/planning` Desktop : **0.58**. Tendance historique montre le saut précisément à partir de la semaine du 16/08 (0.14-0.15 stable avant), partiellement résorbé depuis (0.29) mais toujours élevé.
- `/today` Mobile : LCP p75 4746ms (limite du seuil "bon" 2500ms), CLS 0.162.
- INP globalement bon partout (72-408ms) — les fixes de juillet (dynamic imports /today, fonts self-hosted) ont tenu ; le problème restant est le premier affichage + les sauts de layout, pas l'interactivité.

### Cause racine #1 — bundle public gonflé par l'éditeur de programme
`PublicProgramView.tsx` (`/p/[id]`) importait `SessionTemplateCard`/`avgWeekRpe`/`loadBarColor` depuis `ProgramBuilderModal.tsx` — un fichier qui embarque `@dnd-kit/core`, `AddSessionModal` (→ `ExerciseBlockEditor`, l'autocomplete token-aware), `ReconduireModal`. Tout ce JS de l'éditeur (jamais utilisé sur cette page publique en lecture seule) se retrouvait dans le bundle client de la page la plus visitée par du trafic anonyme — coïncide exactement avec la fenêtre de régression mesurée (le program builder a beaucoup grossi entre le 2 et le 18 août : drawer/DnD/autocomplete/media). **Fix** : extrait dans `src/components/programs/SessionTemplateCard.tsx`, module sans dépendance — `ProgramBuilderModal.tsx` et `PublicProgramView.tsx` importent tous les deux depuis là.

### Cause racine #2 — `useBreakpoint()` bascule mobile→desktop après le 1er paint
`useBreakpoint()` (28 fichiers, dont toutes les pages principales) initialisait toujours à `w=390` puis corrigeait la vraie largeur dans un `useEffect` classique — qui s'exécute **après** que le navigateur ait peint. Tout visiteur desktop voyait donc la mise en page basculer visiblement de mobile à desktop juste après le chargement — exactement ce que CLS mesure, et explique pourquoi `/week` Desktop (0.54) est bien pire que `/week` Mobile (0.29) dans les mêmes données. **Fix** : `useEffect` → `useLayoutEffect` isomorphe (`useIsomorphicLayoutEffect`, repli `useEffect` côté serveur pour éviter le warning SSR) — la correction se fait avant que le navigateur peigne, plus aucun saut visible.

### `next/image` sur l'image de fond `value_intro`
Élément LCP du 1er écran de l'onboarding (`/register`), servi en `<img>` brut (3550×4438px non compressée, hébergée sur `theperfclub.com`). Passé en `next/image` (`fill`/`priority`, redimensionnement + conversion WebP/AVIF auto). `next.config.mjs` : `images.remotePatterns` élargi à `theperfclub.com`/`www.theperfclub.com` (vide avant).

### Temps réel étendu
Jusqu'ici seuls `/today` et `/week` écoutaient `sessions`/`wellness_daily` en direct, et `/coach` n'écoutait que `wellness_daily` (jamais `sessions`/`coach_sessions`) — `/conseils` et `/coach/athletes` n'avaient aucun abonnement, seulement le chargement initial.
- **`ConseilsClient.tsx`** : abonnement `sessions`+`wellness_daily` (RLS `auth.uid()=user_id`, données propres), refetch débouncé (400ms) via `GET /api/conseils?date=...` déjà utilisé par la navigation de date — pas de recalcul client des 42j de baseline.
- **`CoachClient.tsx`** (`/coach`) : nouvel abonnement `sessions` (par sportif réel lié) + `coach_sessions` (propres données du coach), en plus du `wellness_daily` déjà existant. Vérifié en base (`pg_policies`) que RLS autorise bien un coach à lire les `sessions`/`wellness_daily` de ses sportifs liés (`coach_read_athlete_sessions`/`coach_read_athlete_wellness`) — pas besoin de détour par une route admin pour ce cas. Réutilise `handleDateChange` (déjà le mécanisme de rechargement complet), seulement si la vue affichée est "aujourd'hui" — jamais de navigation forcée sur un coach en train de consulter un autre jour.
- **`AthletesClient.tsx`** (`/coach/athletes`) : même principe, `sessions`+`wellness_daily` par sportif réel + `coach_sessions`, refetch débouncé via `GET /api/coach/athletes?date=...` déjà utilisé par la navigation de date.
- `/profil` (`ProfileDrawer.tsx`) laissé de côté — données qui changent rarement pendant qu'un drawer est ouvert, valeur/risque trop faible pour ce chantier.

### `next/dynamic` généralisé sur les modales/drawers
Seul `/today` avait ce traitement (2026-07-28). Étendu à `/week`, `/coach`, `/coach/planning`, `/coach/athletes`, `/conseils` : toutes les modales/drawers ouverts sur demande (`AddSessionModal`/`CoachSessionModal`, `ReconduireModal`/`DuplicateModal`, `WellnessModal`, `ProgramLibraryPage` — qui importe tout `ProgramBuilderModal` → dnd-kit —, `PaywallModal`/`PrimingJourneyModal`, `ProfileDrawer`, `InviteModal`, `AdjustSessionModal`, `TestsPanel` — 1800+ lignes, seulement sous l'onglet Tests) passent de import statique à `dynamic(() => import(...))` — leur JS part dans des chunks séparés, chargés au clic plutôt que dans le bundle initial de chaque page. Composants toujours statiques (rendus inconditionnellement dans le flux principal) : `CalendarHeader`, `DayColumn`/`DraggablePlanning`, `PlanningRing`/`DiffGauge`, `CoachCard`, `AutoregButtons`, `ProgramBanner`, `ShareButton`, `UnsavedBanner`, `SectionTabs`/`RangeToggle`, `ZoneSparkline`/`SparkLineClient`.

### Bug réel corrigé en marge — `sw.js`, exception non gérée sur `cache.put()`
Repéré par Gildas via la console navigateur (`Uncaught (in promise) NetworkError: Failed to execute 'put' on 'Cache'`). Les 2 écritures en cache (fichiers statiques + pages/API) n'avaient jamais de `.catch()` — un fetch annulé (navigation/fermeture avant la fin du téléchargement, plus fréquent depuis les chunks `next/dynamic` ajoutés ce jour) ou une extension qui coupe le flux de réponse fait échouer `cache.put()`, jamais critique (la page reçoit déjà sa réponse séparément) mais remontait comme exception non gérée dans la console. Fix : `.catch(() => {})` sur les deux écritures.

**Autres points de console passés en revue, non touchés** : préchargement de police non utilisé (italique — vérifié utilisé à 6 endroits réels du code, pas du poids mort, garder tel quel) ; `staleTimes:{dynamic:0}` (compromis architectural déjà documenté plus haut dans ce fichier, pas un bug de console à corriger réactivement).

### Requêtes serveur — parallélisation sur `/today`, `/coach`, `/coach/planning`, `/coach/athletes`
Audit complémentaire côté serveur (uniquement pages authentifiées — `/week`/`/conseils`/`/programmes` déjà propres, vérifié) : plusieurs pages enchaînaient des requêtes en série sans dépendance réelle entre elles, presque exclusivement côté coach (une page sportif ne charge que ses propres données, déjà connues dès `getUser()` ; une page coach doit d'abord connaître la liste de ses sportifs avant d'aller chercher leurs données, ce qui crée mécaniquement plus de chaînes de dépendance).
- **`/today`** : `profiles.select("mode, subscription_status")` en amont du `Promise.all` servait uniquement au check de redirection coach, alors que le `Promise.all` juste après fetch déjà `profiles.select("*")` (même donnée, 2 fois). Check déplacé après le `Promise.all`.
- **`/coach`, `/coach/planning`, `/coach/athletes`** : même anti-pattern répété — `profil` (check redirection) puis `coach_athletes` (et `coach_invites` pending pour `/coach/athletes`) en série, alors qu'aucune de ces requêtes ne dépend d'une autre (seulement de `user.id`, déjà connu). Passées en parallèle, redirection vérifiée après.
- **`/coach` en plus** : 2 `Promise.all` séparés (données du jour + historique 14j) fusionnés en un seul à 5 requêtes — le second n'avait jamais dépendu du premier, seulement de `realUserIds`/`allAthleteIds`/`sinceHistory`, connus dès la résolution de `coach_athletes`.
- **Identifié mais volontairement pas touché** : le double `getUser()` (middleware + chaque page, un vrai aller-retour Supabase Auth à chaque fois) — le plus gros levier générique de tous, mais touche la frontière sécurité (faire confiance à un header posé par le middleware plutôt que revalider) ; `coachIsPaying()` vérifiée non-parallélisable (passe forcément par le client admin, RLS `profiles` n'autorise que la lecture de sa propre ligne).

### Vérifié
`tsc --noEmit -p tsconfig.notnext.json` propre après chaque round (dev server de Gildas actif en continu, `.next` jamais touché — piège déjà documenté ailleurs dans ce fichier). Diagnostic PostHog par HogQL direct (clé API personnelle, pas supposé), RLS vérifiée par lecture directe de `pg_policies` en base avant d'écrire le fix temps réel côté coach. **Aucun clic réel par Claude** sur l'ensemble du chantier (jamais de manipulation du compte réel de Gildas) — Gildas a confirmé après coup ne pas percevoir de différence "au feeling", cohérent avec la nature des fixes (statistiques de queue/percentile, pages publiques, scénarios multi-onglets — pas des gains de vitesse perçus en usage normal mono-session).
